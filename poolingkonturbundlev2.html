Совместный продукт Pooling × Контур

Перевозка управляется в 1С.
ЭПД выпускается автоматически.
Клиент не переносит данные руками.

Pooling 1C создаёт объект перевозки внутри 1С ERP — со всей логикой: маршрут, перевозчик, ТС, водитель, статусы. Адаптер Контура.Логистика забирает эти данные и выпускает юридически значимые ЭТрН, заказ-заявку, экспедиторскую расписку, поручение.

Это не интеграция двух систем. Это один транспортно-документарный контур.

Почему клиенты застревают

Четыре боли, с которыми к вам приходят

Каждая из них решается связкой. Используй как открытие разговора.

01

«Данные разбросаны по TMS, Excel, почте и мессенджерам перевозчика» — логист тратит часы на сбор информации для одной ЭТрН. При 50+ рейсах в месяц это производственная проблема.

02

«Нам нужно ЭТрН, но мы не знаем с чего начать — у нас алкоголь, ЕГАИС, несколько экспедиторов» — сложные сценарии откладываются на «потом» годами. Потом станет обязательным.

03

«IT написали кастомную интеграцию под ЭПД, но она ломается на каждом новом XML-сценарии» — поддержка кастомного backend съедает больше ресурсов, чем само решение.

04

«Мы управляем перевозкой вне 1С, поэтому бухгалтерия всё время просит данные заново» — данные перевозки не живут в 1С ERP, а значит каждый документ — ручная работа.

Архитектура решения

Два модуля. Одна цепочка. Ноль ручной работы.

Pooling 1C — управляет перевозкой. Контур — выпускает документы. Граница ответственности чёткая.

данные перевозки → в адаптер
выпуск пакета ЭПД
статусы и документы → обратно в 1С

Pooling 1C — управляет жизненным циклом перевозки

Внутри 1С ERP появляется объект Бронирование — центр перевозки. Хранит: маршрут, даты, паллеты, FTL/LTL, перевозчика, конечного перевозчика, водителя, ТС, статусы, стоимость, историю изменений. Управляемый транспортный контур — не кнопка «отправить в сервис».

Адаптер Контура — формирует и обменивает ЭПД

На основании структурированных данных из Бронирования собирает нужный пакет: ЭТрН, заказ-заявку, экспедиторскую расписку, поручение экспедитору. Учитывает различия для алкоголя и безалкоголки, ЕГАИС, аутбаунда, инбаунда, утилизации, экспедиторских схем.

⚡ Без Pooling 1C

Контур умеет формировать документы — но им нужна основа. Роли сторон, статусы, перевозчик, конечный перевозчик, ТС, водитель, основания, сценарии изменений. Эти данные неоткуда взять без Pooling 1C.

⚡ Без адаптера Контура

Pooling 1C управляет перевозкой, но выпуск ЭПД и юридически значимый обмен документами приходится либо дорабатывать с нуля, либо поддерживать кастомный backend. Масштабировать такое сложнее.

Что получает клиент

Шесть конкретных эффектов — не тезисы, а факты

Единый источник данных

Все параметры перевозки — в Бронировании. Не в TMS, не в Excel, не в переписке с перевозчиком.

Нет ручного переноса

Данные для ЭПД берутся напрямую из Бронирования. Логист не переносит руками ничего.

Быстрее масштабирование ЭПД

Новые типы документов строятся на той же связке — без разработки с нуля под каждый сценарий.

Сложные сценарии — из коробки

Алкоголь, ЕГАИС, аутбаунд, инбаунд, утилизация, экспедиторские схемы — всё учтено. Bacardi уже работает именно так.

Меньше кастомной разработки

Вместо доработки backend под каждый XML-сценарий — готовая экспертиза Контура по ЭПД и Pooling по транспортным процессам.

Контроль изменений

Изменилась перевозка — Pooling 1C пересоздаёт Бронирование, Контур обновляет документы и уведомляет перевозчиков автоматически.

Для продающих подразделений

Два продукта — одна сделка. Как продавать бандл правильно.

Разные ситуации с клиентом — разный заход. Ниже — под каждую команду.

Команда Pooling

Если клиент спрашивает про TMS или ЭТрН в 1С

Твой продукт берёт логику перевозки — покажи что это не просто модуль, а центр управления транспортом внутри 1С. Контур закрывает то, что Pooling не делает — юридически значимый обмен.

Питч: «Pooling 1C даёт перевозке структуру в 1С. Без этой структуры — ни один оператор ЭДО не сможет корректно сформировать ЭТрН»
Демо-сценарий: Показать Бронирование → как данные передаются в адаптер → готовый ЭТрН. Без переноса руками.
Аргумент для IT: «Не нужно поддерживать кастомный XML-маппинг — логика в продуктах двух компаний с сертификацией»
Bacardi-кейс — промышленная эксплуатация, не пилот: алкоголь, ЕГАИС, аутбаунд, инбаунд, утилизация.
Команда Контур

Если клиент спрашивает про ЭПД и не знает откуда брать данные

Адаптер умеет выпускать документы — но ему нужны правильные данные. Без Pooling 1C клиент либо настраивает кастомный маппинг, либо заносит данные вручную. Это и есть боль.

Питч: «Адаптер Контура работает с любым источником данных. Но лучший источник для 1С-клиента — Pooling 1C: данные уже в нужной структуре, ничего руками»
Для финдира: «Вместо двух проектов внедрения — один контур, одно окно поддержки по транспорту и документам»
Аргумент против «сами напишем»: «Кастомный backend работает до первого нового XML-сценария. Потом — снова разработка»
Referral: Передать лид в Pooling на Pooling 1C → совместный онбординг → быстрее к первому ЭТрН.
Работа с возражениями

Четыре вопроса — четыре готовых ответа

Зачитай прямо с экрана. Работает для обеих команд.

Клиент«Зачем два модуля, если можно одним?»

Один модуль — половина пути. Pooling 1C даёт перевозке структуру внутри 1С: роли сторон, статусы, перевозчик, ТС, водитель — без этого адаптер Контура не знает что формировать. Адаптер Контура даёт этой структуре юридическую силу — без него перевозка управляется, но ЭПД не выходит. Вместе они закрывают путь от заявки до подписанного документа без единой ручной операции.

Клиент«У нас уже есть TMS — зачем Pooling 1C?»

TMS не отменяет задачу — она просто живёт снаружи 1С. Pooling 1C создаёт в 1С ERP центральный объект Бронирования, на котором Контур строит документы. Если ваша TMS остаётся — отлично, данные из неё всё равно нужно собрать в одном структурированном месте перед выпуском ЭПД. Эту роль берёт Pooling 1C.

Клиент«У нас алкоголь, ЕГАИС, утилизация — сложно»

Ровно под это решение и строилось. Pooling 1C хранит логику каждого сценария в Бронировании — отдельно для алкоголя и безалкоголки, аутбаунда, инбаунда, утилизации. Адаптер Контура учитывает эти различия при сборке пакета документов. Bacardi работает именно в этой конфигурации — в промышленной эксплуатации, не в пилоте.

Клиент«У нас уже есть своя разработка под ЭПД»

Своя разработка работает до следующего нового XML-сценария. Потом — снова IT, снова спринт, снова деньги. Связка Pooling 1C + Контур закрывает это готовой экспертизой: Pooling — по транспортному процессу, Контур — по всем форматам ЭПД. Расширять backend под каждый новый формат больше не нужно. Вопрос в том, сколько стоит поддержка того, что уже написано.

Формулировка для клиента — одна фраза

Pooling 1C управляет жизненным циклом перевозки внутри 1С ERP. Адаптер Контура формирует и обеспечивает юридически значимый обмен электронными перевозочными документами.

Вместе — не два продукта рядом, а один транспортно-документарный контур: от возникновения транспортной потребности до готового подписанного ЭПД.
